# GearRent backend

## Run locally

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env`.
3. Set `MONGODB_URI` to your local MongoDB or Atlas connection string.
4. Set `BETTER_AUTH_SECRET` to a random secret of at least 32 characters. You
   can generate one with
   `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`.
5. Set `BETTER_AUTH_URL` to the backend origin and `FRONTEND_URL` to the
   frontend origin.
6. Set `BETTER_AUTH_API_KEY` to the key generated by your Better Auth Dash
   project. Do not commit this value or expose it in frontend variables.
7. Start the API with `npm run dev`.

The API listens on port `5000` by default. `GET /api/health` reports whether
MongoDB is connected.
The server uses Cloudflare and Google DNS resolvers for MongoDB Atlas SRV
lookups.

## Authentication

Better Auth handles email/password signup, sign-in, sign-out, and session
management under `/api/auth`. The Better Auth Dash plugin is enabled for
ownership verification and dashboard features; its API key is read from
`BETTER_AUTH_API_KEY`. The frontend registration form creates an account with
`POST /api/auth/sign-up/email`; it sends the profile photo as
Better Auth's `image` field. Passwords must be at least six characters, include
uppercase and lowercase letters, and may be up to 128 characters. Email
verification is not currently required, and successful sign-up starts a
session.

The JWT plugin exposes `GET /api/auth/token` for a signed, 15-minute JWT and
`GET /api/auth/jwks` for its public signing keys. The token endpoint requires an
authenticated Better Auth session. JWTs include the user's `role` claim, which
defaults to `Customer`; browser sessions continue to use Better Auth's
HttpOnly cookies. Do not put access tokens in local or session storage.
For an HTTPS backend, Better Auth cookies use `SameSite=None; Secure` so the
configured frontend can make credentialed cross-origin requests; local HTTP
development keeps `SameSite=Lax`.

Public email signup accepts `role: "Customer"` or `role: "Owner"`; an omitted
role defaults to `Customer`. Other values, including `Admin`, are rejected by
the server. Self-service profile updates cannot change the role. Admin
assignment is an operator-only database action. After
verifying the target account and taking the normal database backup, a trusted
MongoDB operator can promote that account with:

```javascript
db.user.updateOne(
  { email: "admin@example.com" },
  { $set: { role: "Admin" } },
);
```

Run this only in the intended environment with privileged database access; do
not expose an admin-promotion endpoint or credential in the frontend. The
role is included in newly issued JWTs, so have a promoted user sign in again
to obtain a token with the updated role.

`POST /api/auth/update-user` supports self-service updates to `name`, `image`,
`phoneNumber`, and `address`. Phone numbers are optional and must use a
supported international phone format; addresses are limited to 500 characters.
Email changes are not enabled because this app does not yet have an email
verification provider. Account roles cannot be changed through this endpoint.

Google sign-in is enabled when both `GOOGLE_CLIENT_ID` and
`GOOGLE_CLIENT_SECRET` are set. In Google Cloud Console, add
`<BETTER_AUTH_URL>/api/auth/callback/google` as an authorized redirect URI.
Use the exact backend origin configured in `BETTER_AUTH_URL` (including its
scheme); a public HTTPS origin is required for Google's callback in deployed
environments. Leave both variables empty to keep email/password authentication
available without Google sign-in. Email-based password reset is not configured
until an email delivery provider is added.

Better Auth stores its own user, account, and session records in MongoDB. The
MongoDB adapter runs without transactions so it also works with a standalone
local MongoDB server. Existing records from the former custom registration
route are left untouched in the legacy `users` collection and are not
automatically migrated.

The `@better-auth/infra` package uses its default Dash and KV service URLs unless
`BETTER_AUTH_API_URL` or `BETTER_AUTH_KV_URL` are configured. The `sentinel`
plugin remains disabled.

## Equipment roles and permissions

`GET /api/equipment/featured` is public and returns at most six approved
equipment documents. `GET /api/equipment/:id` requires
`Authorization: Bearer <JWT>` from an authenticated Better Auth session and
returns an approved equipment item. Missing, invalid, or expired tokens are
rejected with HTTP 401; authenticated users without the required role receive
HTTP 403.

| Endpoint | Access | Purpose |
| --- | --- | --- |
| `GET /api/equipment/featured` | Public | Browse approved equipment |
| `GET /api/equipment/:id` | Customer, Owner, Admin | Read an approved item |
| `GET /api/equipment/mine` | Owner, Admin | List owned items (Admin sees all) |
| `GET /api/equipment/mine/:id` | Owner of item, Admin | Read a managed listing, including pending items |
| `POST /api/equipment` | Owner, Admin | Create a pending listing |
| `PATCH /api/equipment/:id` | Owner of item, Admin | Edit a listing; it returns to pending review |
| `DELETE /api/equipment/:id` | Owner of item, Admin | Delete a listing |
| `POST /api/uploads/equipment-photo` | Owner, Admin | Validate and upload one equipment image to ImgBB |
| `GET /api/equipment/admin/pending` | Admin | List pending submissions |
| `PATCH /api/equipment/admin/:id/approval` | Admin | Set `approvalStatus` to `approved` or `rejected` |

Every owner mutation is scoped to the JWT subject stored as `ownerId`; changing
an item ID cannot grant access to another owner's listing. New equipment
defaults to `approvalStatus: "pending"` and is not shown in public results
until an Admin approves it. The selected `rentalType` and `rentalPrice` are
stored together. That period uses the exact entered price; other rental periods
are derived from its daily equivalent. Legacy listings without those fields
continue to use `dailyRate`.

## Customer dashboard APIs

The customer dashboard uses the authenticated JWT subject to scope private
records to the current account:

| Endpoint | Access | Purpose |
| --- | --- | --- |
| `GET /api/bookings` | Customer | List the signed-in customer's paid bookings |
| `POST /api/bookings/checkout` | Customer | Reserve equipment and start Stripe Checkout |
| `GET /api/favorites` | Customer | List the signed-in customer's saved equipment |
| `GET /api/favorites/:equipmentId` | Customer | Check whether an item is saved |
| `POST /api/favorites/:equipmentId` | Customer | Save an approved item |
| `DELETE /api/favorites/:equipmentId` | Customer | Remove a saved item |

Booking rows are created only after a verified Stripe payment. Their booking
status is derived from the rental dates: `upcoming`, `ongoing`, or `completed`.
The end date is exclusive, so a booking is completed at the start of its return
date. Favorites and booking queries never accept a customer ID from the caller.

## Owner dashboard APIs

The owner dashboard scopes equipment and rental records to the signed-in owner:

| Endpoint | Access | Purpose |
| --- | --- | --- |
| `GET /api/bookings/owner` | Owner | List paid rentals and active checkout reservations for owned equipment |

Rental rows include a customer name/email snapshot from the checkout token and
the phone number and delivery address provided for that booking. Pending
reservations appear only while their checkout hold is active.

Each equipment document has `name`, `category`, `location`, `dailyRate`,
`rentalPrice`, `rentalType`, `quantity`, `condition`, `brand`, `model`,
`rentalTerms`, `image`, `description`, `approvalStatus`, and (for
owner-created listings) `ownerId`. `dailyRate` is the derived daily equivalent
used by the booking engine. Owner image uploads return an ImgBB HTTPS URL;
legacy records may use a root-relative path.

Example document to add in the `equipments` collection:

```json
{
  "name": "Professional Drill Kit",
  "category": "Power tools",
  "location": "Dhaka",
  "dailyRate": 121.43,
  "rentalPrice": 850,
  "rentalType": "weekly",
  "quantity": 2,
  "image": "/images/tools-rental-banner.jpg",
  "description": "A drill kit for everyday building and repair work.",
  "condition": "Good",
  "brand": "GearRent",
  "model": "GR-100",
  "rentalTerms": "Return the kit clean and in its case.",
  "approvalStatus": "approved"
}
```

## Registration and profile photos

Set `IMGBB_API_KEY` in `.env` to enable profile photo uploads. Get a key from
the [ImgBB API page](https://api.imgbb.com/). Keep the key in the backend
environment; do not add it to a `NEXT_PUBLIC_` variable.

`POST /api/uploads/profile-photo` accepts one `image` file as
`multipart/form-data`, checks its image type and a 5 MB size limit, then returns
the ImgBB URL. This public pre-registration endpoint is rate-limited.
`POST /api/uploads/equipment-photo` uses the same checks and rate limit, and
requires an Owner or Admin JWT. Keep the ImgBB key on the backend; do not add it
to a `NEXT_PUBLIC_` variable.
